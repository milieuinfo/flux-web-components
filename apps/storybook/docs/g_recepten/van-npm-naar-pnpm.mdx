# Van npm naar pnpm

Korte handleiding om de frontend van je toepassing, bvb. in een Maven-project, van npm naar [pnpm](https://pnpm.io/)
om te zetten. Ze is gebaseerd op de migratie bij ARMOS Registraties. Reken op een halve dag, inclusief een groene
build.

**We raden pnpm aan.** De `@domg-wc/*` packages werken technisch met elke package manager, maar kan je (nog) niet
migreren, zorg dan minstens voor een [veilige npm 12](#pnpm-of-een-veilige-npm-12).


## Waarom

- **Veiliger**: install scripts (`postinstall` en co.) draaien enkel voor packages die je expliciet toelaat, en net
  gepubliceerde versies worden standaard niet geïnstalleerd. Dat zijn net de twee manieren waarop recente
  supply-chain-aanvallen binnenkwamen.
- **Strikter**: je code kan enkel packages importeren die in je eigen `package.json` staan. Er sluipen geen
  verborgen (phantom) dependencies meer binnen.
- **Sneller en kleiner**: packages staan één keer in een globale store en worden gelinkt, niet per project gekopieerd.

Voor de backend verandert er niets: Maven installeert Node en pnpm zelf, net zoals vroeger Node en npm.


## pnpm of een veilige npm 12

**Onze aanbeveling is pnpm.** npm 12 (juli 2026) heeft op security veel ingehaald: ook daar draaien install scripts
enkel voor packages in `allowScripts`, en `min-release-age` houdt verse versies tegen. Maar in pnpm 11 staat die
bescherming standaard aan en faalt de install bij een script dat je nog niet beoordeeld hebt. In npm moet je ze zelf
aanzetten, en zonder `strict-allow-scripts` waarschuwt npm enkel. Daarbovenop sluit de strikte `node_modules` van pnpm
phantom dependencies uit.

Kan je nog niet migreren, dan is een **veilige npm 12** het minimum: npm 12 of hoger, een gecommitte
`allowScripts`-lijst in `package.json` en deze instellingen in de `.npmrc` van je project:

```
min-release-age=3
min-release-age-exclude[]=@domg-wc/*
min-release-age-exclude[]=@domg/*
strict-allow-scripts=true
```

Keur een script goed met `npm approve-scripts <package> --no-allow-scripts-pin`. Zonder die vlag pint npm de versie,
en dan matcht de entry na de volgende upgrade niet meer.

Zie een veilige npm 12 als tussenstap, niet als eindpunt: plan de migratie naar pnpm met de stappen hieronder.


## Stappen

### 1. pnpm beschikbaar maken

Vervang in `package.json` het veld `"packageManager": "npm@…"` door een vaste pnpm-versie, of voeg het toe:

```
"packageManager": "pnpm@11.24.0"
```

Doe dit eerst: zolang daar npm staat, weigert corepack om pnpm te draaien. Een upgrade van pnpm wordt zo een bewuste
commit.

Lokaal haal je die versie op met corepack of met Volta. Kies er één per machine.

- **corepack**: `corepack enable`. corepack leest de versie uit `packageManager`. Vanaf Node 25 zit corepack niet
  meer in Node; installeer het dan eerst eenmalig met `npm install -g corepack`.
- **Volta**: Volta negeert `packageManager` en zet `corepack` niet op je `PATH`. Laat Volta pnpm dan zelf beheren: zet
  `VOLTA_FEATURE_PNPM=1` in je shell-profiel en draai `volta install pnpm@11.24.0` en `volta pin pnpm@11.24.0`. Hou
  die versie gelijk aan `packageManager`. Meer bij [Volta - pnpm support](https://docs.volta.sh/advanced/pnpm).

### 2. Lockfile omzetten

In de frontend-map (waar `package.json` staat), met de bestaande `package-lock.json` nog aanwezig:

```
pnpm import
rm -rf node_modules package-lock.json
```

`pnpm import` maakt een `pnpm-lock.yaml` met **dezelfde versies** als je npm-lockfile. Zo verandert de migratie zelf
niets aan wat er geïnstalleerd wordt, en dat houdt het debuggen achteraf eenvoudig.

### 3. pnpm-workspace.yaml toevoegen

In pnpm 11 staat de configuratie in [`pnpm-workspace.yaml`](https://pnpm.io/11.x/pnpm-workspace_yaml) naast
`package.json`, ook als je geen monorepo hebt. Enkel registry en token blijven in `~/.npmrc`, dus je
[Artifactory configuratie](/docs/recepten-artifactory-configuratie--documentatie) werkt ongewijzigd. Andere
`.npmrc`-instellingen negeert pnpm.

**`pnpm-workspace.yaml`**

```yaml
# Packages die tijdens install een script mogen draaien (vervangt allowScripts van npm)
allowBuilds:
  '@swc/core': true
  cypress: true

# Vervangt overrides uit package.json
overrides:
  lit: 3.3.3
  color-parse>color-name: 2.0.0 # geneste override: enkel color-name onder color-parse

# Uitzonderingen op de standaard wachttijd van 24 uur na publicatie
minimumReleaseAgeExclude:
  - '@domg-wc/*'
  - '@domg/*'
```

- `allowBuilds` hoef je niet vooraf te vullen. Bij de eerste `pnpm install` stopt pnpm met `ERR_PNPM_IGNORED_BUILDS`
  en zet het de betrokken packages met een placeholder in dit bestand. Vul per package `true` of `false` in en
  installeer opnieuw (`pnpm approve-builds` doet hetzelfde interactief). Cypress moet op `true`, anders ontbreekt de
  Cypress binary. esbuild, core-js en vue-demi werken ook op `false`; die `false` blijft staan als bewijs dat je het
  package beoordeeld hebt.
- Zonder de uitzondering voor `@domg-wc/*` kan je een nieuwe Flux-release pas 24 uur na publicatie installeren.
  `@domg-wc/components` en `@domg-wc/styles` hebben `@domg/govflanders-style` als dependency. Brengt een release een
  nieuwe versie van die package mee, dan geldt de wachttijd daar ook voor, vandaar `@domg/*`. Publiceert je team zelf
  packages onder een eigen scope, zet die scope er dan ook bij.

### 4. package.json opkuisen

- Verwijder `overrides` en `allowScripts`: die staan nu in `pnpm-workspace.yaml`.
- Vervang `npm` door `pnpm` in de `scripts`, ook waar het genest in een ander commando staat (bvb. in
  `start-server-and-test`). Een achtergebleven `npm install` of `npx` draait alsnog npm.
    - `npm run x -- --flag` wordt `pnpm run x --flag`: pnpm geeft een `--` letterlijk door aan je script.
    - `npx x` wordt `pnpm exec x` voor een geïnstalleerde binary, of `pnpm dlx x` voor een package dat je niet
      installeerde.
- Zet `package-lock.json` in `.gitignore`.
- Optioneel: laat npm meteen weigeren met `devEngines`. npm 10.9 en hoger stopt dan bij elk commando met
  `EBADDEVENGINES`. Zet in `version` exact dezelfde waarde als in `packageManager`.

  ```
  "devEngines": {
      "packageManager": { "name": "pnpm", "version": "11.24.0", "onFail": "error" }
  }
  ```

### 5. Maven (frontend-maven-plugin)

In de plugin-configuratie wordt elke `npm` een `pnpm`:

- `<npmVersion>` wordt `<pnpmVersion>`, met dezelfde versie als in `packageManager`.
- `<npmDownloadRoot>${acd.repository.npm.dist.url}</npmDownloadRoot>` wordt
  `<pnpmDownloadRoot>${acd.repository.pnpm.dist.url}</pnpmDownloadRoot>`.
- Goal `install-node-and-npm` wordt `install-node-and-pnpm`.
- Goal `npm` wordt `pnpm`.

De `<arguments>` (`install`, `run build`, …) blijven hetzelfde.

### 6. Jenkins

Draait je pipeline ook npm-commando's buiten Maven om, vervang die dan:

```groovy
// was
sh 'npm ci'

// wordt (--frozen-lockfile: de lockfile mag niet veranderen)
sh 'pnpm install --frozen-lockfile'
```

Een `--maxsockets 5` wordt `--network-concurrency 5`. Scan je de lockfile met Trivy, pas dan het pad aan naar
`pnpm-lock.yaml`.

Staat pnpm niet op je build-agent, installeer het dan met npm. corepack kan pnpm niet ophalen via een Artifactory met
authenticatie (de tarball geeft 403), npm gebruikt je `.npmrc` wel. Lees de versie uit `packageManager`, dan blijft
er één bron van waarheid:

```
PNPM_VERSION="$(node -p "require('./package.json').packageManager.replace(/^pnpm@/, '').split('+')[0]")"
npm install -g "pnpm@${PNPM_VERSION}"
```

### 7. Builden en fixen

Draai de volledige build (`mvn verify`) en los op wat breekt. Wat de afnemer tegenkwam:

        <tr>
            <td>Native binaries (SWC, …) ontbreken in een Linux-container</td>

**`jest.config.mjs`**

```js
transformIgnorePatterns: ['/node_modules/(?!\\.pnpm/|(?:lit|lit-html|@lit)/)'],
```

**`pnpm-workspace.yaml`**

```yaml
# Linux-containers (glibc én musl) naast je eigen platform
supportedArchitectures:
  os: [current]
  cpu: [current]
  libc: [glibc, musl]
```
